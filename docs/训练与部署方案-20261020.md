# 训练与部署方案 · 2026-10-20

> **对象：我这台鸭子**（15 颗飞特 HD-1910 已在 Mac 调试台完成一键校准、方向核对、供电排查；主控上电自检通过）。
> 口径与 [我的记录](../我的记录.md) 一致：只写我自己的进度。上游第一台（kissqy 整套那台）的历程当**参考证据**用，不当本机进度。

## 0. 一句话结论

**别把「训练」当第一步。** 正确的顺序是：

```
主控跑通（先把跑道铺出来）
      ↓
台架辨识（把仿真参数对齐到真机）
      ↓
训练（平地速度 + 转向）
      ↓
部署 + 同条件 A/B 评估
      ↓
用真机数据回灌，再训
```

两个理由：

1. **训练要用真机参数喂。** 换舵机（XL330 → HD-1910）本身「不强制重训」，重训的理由是**本体差异**：单颗重 3 g（整机 +45 g）、质心挪了、堵转力矩 2.5 倍、回差、脚的摩擦都不同。参数不对齐就开训，等于把 10-12～10-14 那轮「推摇杆走两三步就摔」再走一遍，而且这次是花 GPU 时间摔。
2. **评估要有参照物。** 上游第一台已经用 kissqy 的模型 + 陀螺融合走起来了（推摇杆 60 s 一次没摔）。这条链路**可以在我自己的鸭子上先复现**——当天就能拿到「会走 + 能采数据」的基线。有了它，自训出来的策略才有得比；没有它，你连「新策略是好是坏」都判不了。

## 2. 先做三个决策

### 决策一：部署走哪套运行时（最大的一处分叉）

| | A · kissqy 整套 + 我们 I2C IMU 补丁 | B · 官方运行时 + `FeetechIo` fork | C · 自己的 Python 运行器 |
|---|---|---|---|
| 上真机验证过吗 | **走过**（上游第一台，推摇杆 60 s 不摔） | ❌ 没上过板 | 只用来调试，不具备部署能力 |
| IMU | I2C 模块（BNO085 / LSM6DSV16X） | `imu_to_dxl` 小板挂总线 ID 200；`imu_ready()` 目前恒 false，**要补 `ImuSource`** | — |
| 模型从哪来 | kissqy 的训练包 | 自己的 ONNX | — |
| 许可 | 他的中控是个人非商业许可，不许公开/提 PR | Apache-2.0，将来能提 PR 回上游 | 本仓库 |
| 定位 | **先当「跑道」**：快、已验证 | **当「主线」**：干净、可持续 | 仅调试台 |

**建议：A 先跑起来，B 并行养。** 不是二选一——A 负责「今天就有一条能走、能采数的链路」，B 负责「以后自己的策略有干净的部署位」。两条的切换点就是你第一次训出 ONNX 的时候。

### 决策二：IMU 走哪条路

- **I2C 模块**（现状、A 路线要用的）——便宜、接线简单；上游踩过的坑都在（装歪 8.5°、走路时芯片姿态乱跳 → 必须开 `bno08x_fusion = "gyro"`、固定方式从胶粘改螺丝）。
- **`imu_to_dxl` 小板**（B 路线要用的）——我这块板子要不要打样？固件的模拟验证和 SWD 台架观察已经做了，**真混合总线没验收**。

> 建议：**短期走 I2C 模块**（复用上游已经踩平的坑），小板作为长期选项排到 B 路线后面。

### 决策三：训练机器与训练目标

- **机器**：本地 NVIDIA CUDA（Linux 或配好 GPU 的 WSL2）最好；没有就用 `--hf-jobs` 提交到 Hugging Face 托管 GPU（工程里已经接好，连 wandb 都会转发）。
- **目标**：**平地速度 + 转向**（`Mjlab-Velocity-Flat-MicroDuck-HD1910`）。
- **暂时不碰**：地形/斜坡、球、ground_pick、头颈姿态跟踪。这些是后面的事。

## 3. 阶段 0 · 先把跑道铺出来（1–2 天）

**目的**：在自己这台机器上拿到「鸭子会走 + 能采数据」的基线。

1. 定 A 路线：我的卡上装 kissqy V167 那一套 + I2C IMU 补丁。**注意：装了自己改过的 robotd 之后，别点 kissqy 中控里的「安装 / 升级固件」**，会把 IMU 支持冲掉。
2. IMU 上机：模块固定（螺丝，不是胶）、按四方向检查确认 mount 四元数、站 HOME 校零点、开 `bno08x_fusion = "gyro"`。
3. 舵机参数：**先 P5 / D0 / 默认**（跟训练模型一致；真机带 D 会颤，D=20～40 时高频颤 51%，D=0 降到 4–8%）。
4. 上机顺序（不许跳）：趴着只读 → 卸力 → 托着测姿势 → 放地上短时 → 逐步加时长。
5. 顺手把两件保命的事做了：**10 A 级电源**（整机走路会掉电，这不是软件问题）、**关掉吃 CPU 的常驻服务**（`duck-quiet.sh`）。
6. 采一轮基线数据：`onboard-analysis/` 的 50 Hz 录像 + 电压温度 + IMU 日志；顺手称整机重量。

**验收**：推满摇杆连续走 ≥ 20 s 不摔；整机不重启；控制环稳在 20 ms（不掉到 25 ms）。

## 4. 阶段 1 · 台架辨识（2–5 天，和 GPU 侧并行）

按 [训练前数据清单](HD-1910训练前数据清单.md) 做，但**砍到影响仿真保真度的最小集**——不用全做。

**台架**：URT-2 + 可调电源（7.4 V / 2 A）+ 摆杆 + 记录脚本（`tools/servo-web/` 那套已经能连）。

| 优先级 | 测什么 | 参数 | 为什么 |
|---|---|---|---|
| ★★★ | 阶跃响应 | ±10° ×5 次 | 命令延迟、上升时间、超调 → 直接对 BAM 的 `kt / R / armature / delay` |
| ★★★ | 整机重量 + 质心 | 称重法；含电池 | 换舵机后 +45 g，各刚体质心都挪了 |
| ★★★ | 脚的摩擦 | 倾斜平面法，地板/瓷砖/地毯各 5 次 | 抓地力决定能不能走起来（换硅胶前后差别很大） |
| ★★ | 摆锤四条轨迹 | 6.6 / 7.4 / 8.2 V × P 100/200/300 × 负载 0/0.05/0.1 kg，50 Hz、每段 20 s | 辨识摩擦/回差，覆盖 2S 电池全电压区间 |
| ★★ | 回差 | ±1° / ±2° ×5 次（外部量角器，编码器量不到自己） | 对厂家 ≤0.5° |
| ★★ | IMU 静止 | 60 s 漂移 + 前后左右各倾 10° | mount 与零点 |
| ★ | 总线时序 | 真机 50 Hz 下错误率/抖动 | **换 HAT/转接线后这里是第一个要看的数**：错误率不为 0 就是方向切换跟不上 1 Mbps |
| ★ | 低速 / 重复性 | — | 可选 |

**产出**：
1. 一份**我自己的**执行器参数 JSON（先跟 M6 并排比，差多少写清楚）；
2. 一张**domain randomization 范围表**——每项的实测值和要给 DR 留的余量。

## 5. 阶段 2 · 仿真对齐（1–2 天）

不用 GPU 也能做一半。

1. **单舵机层**：拿辨识出来的轨迹喂 `validate_bam_testbench.py` / `testbench_sim2real.py`，叠图对上升时间、超调、稳态误差。
2. **整机层**：用 `tools/gait-analysis/` 的脚本，把仿真和真机的**同一组指标**摆一起——站姿横滚、撑地膝盖角、抬脚高度（真机 3–6 mm vs 仿真 11–12 mm）、高频颤占比、统一缩放 0.83 vs 1.0、滤波器设置。
3. **修 DR 范围**：质量/惯量（±5% 是不是够）、关节摩擦、编码器偏置、电压区间、延迟（3–6 步 = 15–30 ms 要不要改）。
4. **对齐原则**：仿真里的条件必须**盖住**真机，而不是等于真机——「越抓地越容易摔」那轮就是仿真里脚太滑、真机太抓，模型没学过。

**验收**：阶跃的上升/超调和稳态差在可接受范围内；抬脚高度仿真 ≈ 真机。

## 6. 阶段 3 · 训练（3–7 天）

```bash
cd software/training
uv sync --frozen --python 3.12

# 1) smoke：先确认链路（64 环境 × 5 轮）
MICRODUCK_TOTAL_MASS_KG=0.850 uv run --frozen train Mjlab-Velocity-Flat-MicroDuck-HD1910 \
  --env.scene.num-envs 64 --agent.max-iterations 5 \
  --agent.logger tensorboard --agent.run-name hd1910_smoke

# 2) 正式（本地 GPU；没有就加 --hf-jobs 交到托管 GPU）
MICRODUCK_TOTAL_MASS_KG=0.850 uv run --frozen train Mjlab-Velocity-Flat-MicroDuck-HD1910 \
  --env.scene.num-envs 4096 --agent.max-iterations 4000 \
  --agent.logger tensorboard --agent.run-name hd1910_v1
```

**`MICRODUCK_TOTAL_MASS_KG` 是 M2 的占位校准**：不设 = 上游原值（仿真 737.2 g）；
设成你实称的整机质量（现在是 **0.850**）后，仿真会把 15 个刚体的质量 + 惯量
**等比**缩放（先按整机比例，因为还没分段称）。这是「一阶修正」，不是 M2 的替代品 ——
M1 台架把躯干 / 头 / 每条腿分段称出来之后，要换成**逐刚体实测值**。
代码在 `software/training/src/mjlab_microduck/robot/microduck_constants.py`（`_robot_spec`）。

- **入口**：`Mjlab-Velocity-Flat-MicroDuck-HD1910`；奖励/课程**先照抄上游**，别一上来加花活。
- **中途盯**：`nan_state`（必须恒 0）、episode 长度、速度跟踪误差、力矩/能耗、抬脚高度。
- **导出**：
  ```bash
  MICRODUCK_TOTAL_MASS_KG=0.850 uv run --frozen python scripts/export.py Mjlab-Velocity-Flat-MicroDuck-HD1910 \
    --checkpoint 4000 --onnx-file duck_hd1910_v1.onnx
  ```
  导出后校验输入 `[1,61]`、输出 `[1,14]`、输出有限值、关节顺序与本地 Microduck 一致。
- **版本**：run name 带日期 + 关键参数摘要（env 数、迭代、DR 版本）。

## 7. 阶段 4 · 部署上机（2–3 天）

1. **安全前置**（每次上机都要走一遍）：软起步、低压线 ≥ 6.6 V、转矩上限、D=0 或 D=5～10、网页/常驻服务停掉。
2. **上机阶梯**：趴着只读 → 卸力 → 托着跑姿势 → 短时松手 → 逐步加时长。
3. **记录**：`onboard-analysis/` 全程采数。
4. **A/B**：新策略和阶段 0 的 kissqy 基线**同条件、同一张桌面、同一双鞋底**各走一组。

**验收**：新策略至少不差于基线；能量化说出好在哪、差在哪。

## 9. 已知的坑（照抄上游的代价，不用再付一遍）

| 坑 | 现象 | 处理 |
|---|---|---|
| 台式电源 CC 限流 | 15 颗同时掉线，电压掉到 4 V | 电流旋钮调到 2 A+；面板 **CV 亮正常、CC 亮被限流** |
| 整机走路掉电 | 新旧卡都会 | 10 A 级电源；同时记电池端和舵机总线端 |
| 主板过热降频 | 84–87 ℃、CPU 锁 408 MHz、控制环 25 ms | 停网页服务 `duck-quiet.sh` |
| BNO085 姿态乱跳 | 20 ms 内跳 20–60°，模型以为在倒 | `bno08x_fusion = "gyro"`（默认是 chip，要自己切） |
| IMU 装歪 | 8.5° 偏差，策略一接管就冲 | HOME 之后再标定；固定改螺丝 |
| 舵机 D | 训练模型里没有 D，真机带 D 会颤 | D=0；P3 时机身晃动才跟仿真一样 |
| 参数写在 RAM 还是 EEPROM | 上力时写 RAM、卸力恢复；上着力重启 robotd 鸭子当场瘫 | 切回原版前给舵机断一次电 |
| kissqy 中控的「安装/升级固件」 | 会装回原版 robotd，冲掉 I2C IMU 补丁 | 装了自己改的 robotd 就别点 |
| 一键校准的「写 128」 | HD-1910 固件不认 | 走 0x0B 位置校准指令 |

## 11. 今天就能动的三件事

1. **定决策一**（A 还是 B 先跑）——你拍板，我接着帮你把卡上的安装步骤、IMU 接线和 `robotd.toml` 逐项核对成一张可执行的清单。
2. **把台架搭起来**，先只做 ★★★ 那三项（阶跃、称重、脚摩擦）——不用等 GPU，也不依赖跑道。
3. **找一台 CUDA 机器跑一次 smoke**，确认训练链路在你自己的机器上是通的（用得上再加 `--hf-jobs`）。
